#9 Register Student (Backend) + #10 (Frontend)
-----------------------------------------------
The student number is generated by the System, not entered by Staff.
- Step 3: the Staff enters name, personal email, degree programme and curricular year.
- Step 6: the System generates the student number, institutional email and one-time password.
- Remove the "the student number already exists" alternative scenario.
- Business rule typo: "umber@institution domain" -> "number@institution domain".
- Business rule (new, 2026-10-16): the institutional email is "number@students.<institution
  domain>" (e.g. 50001@students.studymatch.com). The domain is set in the System's
  configuration, never typed by Staff.


#17 Create Account (Backend) + #23 (Frontend)
----------------------------------------------
Same as Register Student: the employee number is generated by the System.
- Step 3: the Admin selects the account type and enters name and personal email.
- Step 6: the System generates the employee number, institutional email and one-time password.
- Remove the "the employee number already exists" alternative scenario.
- Business rules: remove "the one-time password ... expires after 7 days". It stays valid
  until the user changes it at first login.
- New (2026-10-16): Staff and Teacher institutional emails are no longer generated from the
  employee number. The Admin types the part before the "@", freely chosen (it doesn't have to be
  the person's name, e.g. joao.silva or js42); the form shows "@<institution domain>" fixed,
  and the System adds it (joao.silva@studymatch.com).
  - Step 3: "... enters the user's name, personal email and institutional email username".
  - Step 6: "the System generates the employee number and one-time password".
  - New alternative: the institutional email is already in use -> warning.
  - Business rule: replace "generated from the employee number" with the rule above. Only
    lowercase letters, digits and dots are allowed before the "@".

#64 Edit Student Statute (Backend) + #65 (Frontend)

A student holds at most one statute at a time, with no history.
- Step 3: the System displays the student's current statute (no past statutes).
- Step 5: the Staff selects the type and the end date only (no start date; it starts when added).
- Adding a statute replaces the current one, if any.
- "Ends an active statute": the statute is removed (not end-dated today).

#19 Register Subject (Backend) + #20 (Frontend)

- Step 2: categories are now managed by Staff (see "Register Category" below).

#57 Generate Groups (Backend) + #56 (Frontend)
----------------------------------------------
The preview is saved as Draft groups (so it can be opened in Edit Groups, which already

- Step 8: the System changes the groups' status to Published.

#38 Register Attendance (Backend) + #39 (Frontend)
--------------------------------------------------
A class can have several lessons on the same day, so a lesson is identified by its start time.
- Step 4: the Staff selects the subject, class, date and start time of the lesson.
- "The selected date is in the future" -> "the selected date and time are in the future".


#66 Start Academic Year (Backend) + #67 (Frontend)
---------------------------------------------------
An academic year is just its start year (2026 = 2026/2027), with no dates, label or
"is current" flag. The current year is always the latest one.
- Step 2: the next year is always the current one + 1 (or, if none exists yet, derived
  from today's date: September onwards = this year, otherwise last year).
- Step 4: "sets it as current" is implicit, since it's now the latest year.
- Remove the "the academic year already exists" alternative scenario (it can't happen).
- Business rule "only one academic year is current at a time" holds by design.


CLASS DIAGRAM CHANGES (docs/SM_ClassDiagram.jpg)
================================================

User (abstract)
- number is generated by the System.
- + password, + mustChangePassword.
- institutionalEmail: Students get number@students.<domain> (generated); Staff, Teachers and
  Admins get <username chosen by the Admin>@<domain>. The domain is configuration, not data.
- + resetCodeHash, + resetCodeExpiresAt, + resetCodeAttempts (Forgot Password #118): one active
  code per User at a time, only its hash is stored. Methods startPasswordReset,
  hasActiveResetCode, registerFailedResetAttempt, clearPasswordReset.

Student
- + degree (many Students -> 1 Degree, required).
- personalityProfile: optional, wiped every academic year.
- skills, interests: lists of short texts instead of one text.
- languages: set of the Language enum (Language is no longer a class).
- statuteType + statuteEndDate (one statute at a time, none = empty).
- Remove the duplicated Student box at the bottom (next to Separation).

Language
- Class -> enum.

PersonalityProfile
- Traits are placeholders, each a decimal from 0 to 1.

AcademicYear
- Only startYear (2026 = 2026/2027). Remove label, startDate, endDate, isCurrent.

Degree
- + name.

Subject
- cod -> code. Keep name, ects (whole number).
- category becomes an association to the new Category class.
- curricularYear and semester move to DegreeSubject.
- Degree 1 -- 1..* Subject becomes Degree * -- * Subject through DegreeSubject.

DegreeSubject (new)
- degree, subject, curricularYear, semester. One per (degree, subject) pair.

Category (new)
- name. Subject * -- 1 Category.

SubjectEdition
- Teacher 1 -- 0..* SubjectEdition becomes Teacher 1..* -- 0..* SubjectEdition.
- One per (subject, academic year).

ClassSection
- code is unique within its SubjectEdition.

Lesson
- date -> startsAt (date and time). One per (class section, start time).

Enrolment
- status: EnrolmentStatus enum (IN_PROGRESS, PASSED, FAILED). Passed = final grade >= 10.
- One per (student, subject edition).

Assignment
- type: AssignmentType enum (PROJECT, EXAM, PRACTICAL_EXAM).
- weight: fraction of the final grade (0.01 to 1.00, e.g. 0.35).

Grade
- value: 0 to 20, decimals allowed. One per (enrolment, assignment).

Absence
- One per (lesson, enrolment).

Assignment -- GroupingRule
- Assignment 1 -- 0..1 GroupingRule (only Projects have one; none = individual work).

GroupingRule
- isSameClass kept. + association to its Separations (1 -- 0..*).
- Sizes must satisfy 2 <= minSize <= optimalSize <= maxSize.

Separation
- Exactly 2 Students (a pair), not 2..*. Remove the Separation 0..1 -- 1 GroupingRule
  multiplicity and use GroupingRule 1 -- 0..* Separation.

Group
- status: GroupStatus enum (DRAFT, PUBLISHED).
- number is unique within its Assignment.
- explanation stays (calculated from the current members).

TutorApplication
- status: TutorApplicationStatus enum (PENDING, APPROVED, REJECTED).
- The Teacher association is the Teacher who decided it (0..1 until decided).
- Subject 1 -- 1..* TutorApplication -> Subject 1 -- 0..* TutorApplication.

TutorRole
- One per (student, subject). Never ends.

Rating
- One per attended StudyRoom: Participation 1 -- 0..1 Rating (as in the diagram).
- updatedAt -> ratedAt (ratings are never updated, a new one is created).

StudyRoom
- Hosted by a TutorRole (StudyRoom 0..* -- 1 TutorRole), which gives both the tutor and
  the subject. If the diagram links StudyRoom straight to Student, point it to TutorRole.
- status: StudyRoomStatus enum (SCHEDULED, FULL, CANCELLED, COMPLETED). FULL is calculated
  (participants = capacity), never stored.
- + cancellationReason (optional, #53).
- link: the Google Meet link, entered by the Tutor (required).

Participation
- One per (study room, student). hasAttended is set by the Tutor in Confirm Attendance.

Achievement
- Class -> enum (the list is a placeholder, see "To revisit later"). name, description,
  logo and criteria move out of the backend: name/description are frontend translations,
  logo is a frontend image per code, criteria are checked in the service.

EarnedAchievement
- One per (student, achievement); never removed.
- verificationCode: generated by the System, unique, shown as a QR on the certificate.
- Achievement 1 -- 1..* EarnedAchievement -> 1 -- 0..* (an achievement nobody has earned).

Enums to show: AccountStatus (ACTIVE, BLOCKED), StatuteType (WORKING_STUDENT,
HIGH_PERFORMANCE_ATHLETE, STUDENT_ASSOCIATION_LEADER, STUDENT_PARENT, SPECIAL_NEEDS),
Language, EnrolmentStatus, AssignmentType, GroupStatus, TutorApplicationStatus,
StudyRoomStatus, Achievement, Role (ADMIN, STAFF, TEACHER, STUDENT; each user type returns
its own role).

Register Degree (Backend + Frontend)
------------------------------------
Actor: Staff. The Staff registers a new degree programme by entering its name.
- Alternative: a degree with that name already exists -> warning.

Update Degree (Backend + Frontend)
----------------------------------
Actor: Staff. The Staff renames an existing degree programme.
- Alternative: a degree with that name already exists -> warning.

Register Category (Backend + Frontend)
--------------------------------------
Actor: Staff. The Staff registers a new subject category (GR3) by entering its name.
- Alternative: a category with that name already exists -> warning.

Update Category (Backend + Frontend)
------------------------------------
Actor: Staff. The Staff renames an existing category.
- Alternative: a category with that name already exists -> warning.

Change Student Class (Backend + Frontend)
-----------------------------------------
Actor: Staff. The Staff moves an enrolled Student to another class of the same Subject Edition.
- Alternative: the class belongs to a different Subject Edition -> not allowed.
- Existing grades and absences stay with the enrolment.
